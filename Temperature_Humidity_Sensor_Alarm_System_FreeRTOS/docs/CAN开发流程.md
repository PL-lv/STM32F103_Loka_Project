## 2. 期望成品与职责

```mermaid
flowchart LR
    D[DHT11] --> A[A 环境端：持续采样与 CAN 上报]
    A --> TA[TJA1050 A]
    TA <-->|CANH / CANL / 共地| TB[TJA1050 B]
    TB --> B[B 管理端：接收与数据状态管理]
    B --> O[OLED：温湿度 / 在线状态 / 故障]
    K[五个按键] --> B
    B --> W[LED 与蜂鸣器]
    B <--> F[W25Q64：阈值保存]
    B --> H[RAM 历史记录]
    B --> P[串口上位机]
```

| 功能 | A 环境端 | B 管理端 |
|---|---|---|
| DHT11 | 上电后持续采样，每 2 秒尝试一次 | 不再直接采集 |
| CAN 数据 | 每次采样尝试后报告结果，读取失败也报告故障 | 校验、解析并更新最新数据 |
| 心跳 | 每 1 秒发送，传感器故障不停止心跳 | 判断 A 是否在线 |
| OLED | 本地诊断显示，当前显示身份和运行计数 | 温湿度、状态和管理菜单 |
| 五个按键 | 不安装 | 沿用现有操作 |
| 温湿度阈值 | 不保存、不判断 | 唯一配置来源，负责比较和报警 |
| LED / 蜂鸣器 | 不安装业务报警 | 环境超限与设备/通信故障分开提示 |
| W25Q64 | 不安装 | 沿用双扇区阈值保存与恢复 |
| 历史数据 | 不保存 | 保持 RAM 最近 4 条有效采样，掉电不保留 |
| UART | 可保留调试输出 | 保留数据上报，最后回归现有 Python 上位机 |

优化理由：阈值、交互、存储和报警都属于 B 的管理职责，放在同一端可避免两端配置不同步。本轮不增加“经 CAN 修改 A 的报警阈值”的命令，因为 A 不使用该阈值。

A 必须持续采集和发送，不能依赖 B 的菜单状态。B 的 RUN/STOP 只控制管理端是否启用监测报警、RUN 页面刷新和历史记录；STOP 或进入设置时，后台仍接收 CAN 并更新在线状态。

### 2.1 保留的按键语义

| 按键 | B 端用途 |
|---|---|
| K1 | 启用/停止 B 的监测报警；不停止 A 的采样 |
| K2 | 菜单确认 |
| K3 / K4 | 选择菜单、调整阈值 |
| K5 | 设置/返回；在阈值编辑页按现有规则保存两个阈值 |

阈值仍为 0～99 的现有菜单范围，温度默认 40、湿度默认 60。修改先反映到 RAM，明确保存成功后才声称已持久化；未变化不重复擦写。

### 2.2 数据与报警规则

1. 只有收到新的一次有效采样，才更新“最后有效数据”的时间、插入历史和驱动正常环境判断。重复帧、错误帧不刷新有效数据年龄。
2. B 上电且尚无有效采样时显示等待数据，不能把初始化的 0/0 当作真实环境。
3. 心跳每 1 秒一次，B 超过 3 秒没有新的有效心跳，判定通信离线。
4. 心跳正常但传感器明确上报失败，提示传感器故障；最后有效采样超过 5 秒未更新，也转为数据过期/采样故障。
5. 失效数据不能继续被当作实时值比较阈值。可以显示最后值，但必须标注无效或过期。
6. RUN 时提示优先级：通信离线 > 传感器故障/数据过期 > 温湿度超限 > 正常。温湿度超限沿用现有 500ms 声光节奏；通信/采样故障采用不同文字和提示节奏，具体节奏在 S05 设计。
7. STOP 时声光关闭，在线/故障状态仍可查看；进入设置不会阻止后台通信。
8. 通信恢复后，必须拿到新的有效采样才恢复正常环境判断。仅收到心跳不足以证明测量已恢复。
9. A 或 B 重启、采样序号回绕都要处理；不能使用简单的“新序号必须大于旧序号”判断新消息。

本轮不增加 CANopen、CAN FD、远程升级、历史落盘、新传感器和完整上位机界面重做。第三节点用于后期验证，不阻塞主线成品。

## 3. CAN 协议 V1 约定

本节作为 S02/S03 的接口依据；修改字段时先更新本文。A 端 0x181/0x701 发送在 S03.2 实现；B 端解析与显示在 S04.1 实现，量程校验、重复帧丢弃、漏帧线索、离线与数据过期判定在 S04.2 实现。

- 经典 CAN、11 位标准数据帧、500 kbit/s、DLC 固定为 8；不使用遥控帧或扩展帧。
- 当前系统时钟配置为 72MHz，APB1 为 36MHz。计划采用 Prescaler=6、BS1=9tq、BS2=2tq、SJW=1tq，实际构建与总线阶段再核对。
- 采样数据与心跳分开：A 活着不等于 DHT11 正常。
- 多字节无符号数使用小端；字段逐字节打包，不直接发送 C 结构体内存。

| ID | 发送者 | 用途 | 周期 |
|---|---|---|---|
| 0x181 | A | 温湿度采样结果 | 每次采样尝试后，约 2 秒 |
| 0x701 | A | 心跳、传感器状态、运行时间 | 1 秒 |
| 0x581 | A/B/C，仅联调且每次只启用一个发送者 | 固定帧收发、过滤器实验 | S02.3 A 每秒发送；反向测试后续再加 |

0x181 数据：D0=协议版本 1，D1=本次采样尝试序号（8 位回绕），D2=温度整数 ℃，D3=湿度整数 %RH，D4=结果（0 有效，1 读取/校验失败），D5～D7=0。

结果失败时 D2/D3 置 0 作为占位；B 依据 D4 判断，绝不能把占位解释为真实的 0℃/0%RH。V1 温度采用现有 DHT11 的非负整数表示；换支持负温度的传感器时需升级协议。

0x701 数据：D0=版本 1，D1=心跳序号，D2=采样状态（0 等待首次采样，1 最近采样成功，2 最近采样失败），D3=最近一次采样尝试序号，D4～D7=上电运行毫秒数（uint32，小端）。

B 校验 ID、IDE、RTR、DLC、协议版本和数据范围。序号和运行时间用于识别重复消息、丢帧线索及重启；时间差要按无符号回绕方式计算。离线检测使用 B 自己的接收时刻，不要求两块板时钟同步。

正式业务阶段 B 不向 A 写阈值。0x581 为独立联调帧，不按温湿度业务格式解释：S02.3 先做 A→B，反向测试后续再加。DLC=8，D0～D6 固定为 01 02 03 04 05 06 07，D7 为每次尝试递增的 8 位序号（0～255 回绕，失败也消耗序号）。不能将联调帧包装成已完成的远程业务；以后新增控制命令时再设计请求序号、参数校验和应用响应。

## 4. 最终接线

### 4.1 两端相同的 CAN、供电与下载连接

| 连接 | A 板 | B 板 | 说明 |
|---|---|---|---|
| TJA1050 TXD / TX | PA12 | PA12 | MCU CAN_TX → 收发器输入，不按串口方式交叉 TX/RX |
| TJA1050 RXD / RX | PA11 | PA11 | 收发器输出 → MCU CAN_RX |
| TJA1050 VCC | 对应 ST-Link 标注的 5V | 对应 ST-Link 标注的 5V | 用户已确认当前接法；可实测模块处 4.75～5.25V |
| TJA1050 GND | A 板 GND | B 板 GND | 板、收发器、下载器共地 |
| TJA1050 S（若引出） | GND | GND | 正常高速模式；若模块内部已处理，按模块电路核对 |
| SWDIO | PA13 | PA13 | 保留 |
| SWCLK | PA14 | PA14 | 保留 |
| UART TX（可选） | PA9 | PA9 | 接 USB-TTL 的 RX，TTL 逻辑使用 3.3V |
| UART RX（预留） | PA10 | PA10 | 当前 USART 驱动只启用 TX，不代表已实现串口命令 |

两块板各自维持原先已验证的 ST-Link 供电方式。CAN 跨板连接 CANH、CANL、GND；不要把两套下载器的 5V/3.3V 电源输出互相并接。STM32 的 3.3V 电源脚不能接入收发器这路 5V。

TJA1050 是 5V 收发器，TXD 输入可识别 3.3V；其 RXD 属于 5V 侧信号。PA11 为 FT 引脚，作为数字输入使用，并关闭内部上下拉，采用浮空输入。PA12 采用复用推挽输出。MCU 正常供电时才能按该条件连接。

PA11/PA12 同时也是 MCU 原生 USB 数据引脚，本轮不使用 MCU 的 USB 通信。ST-Link 的 USB 插在下载器上，不占用目标板 PA11/PA12；目标板板载 USB 元件是否额外加载 PA12，需按具体开发板电路检查。

### 4.2 A 环境端外设

| 外设引脚 | A 板连接 | 供电 / 说明 |
|---|---|---|
| DHT11 DATA | PA0 | 沿用现有驱动 |
| DHT11 VCC | 3.3V | 用户确认当前供电为 3.3V，迁移后保持；PA0 不属于 FT 引脚，数据上拉不接 5V |
| DHT11 GND | GND | 共地 |
| OLED SCL / SDA | PB8 / PB9 | 使用与 B 相同的 I²C OLED 和现有驱动 |
| OLED VCC / GND | 3.3V / GND | 适用于支持 3.3V 供电的同款模块；按模块丝印接线 |

A 不接业务按键、报警 LED、蜂鸣器和 W25Q64。OLED 用于本地诊断，调试串口可选。

### 4.3 B 管理端外设

| 外设 | B 板引脚 | 接法 / 用途 |
|---|---|---|
| OLED SCL / SDA | PB8 / PB9 | 保持原有软件 I²C，模块原供电保持不变 |
| K1～K5 | PA1～PA5 | 独立按键另一侧接 GND，内部上拉，低电平按下 |
| 报警 LED 控制 | PA6 | 从原 PA11 迁移，保留原有限流与低电平点亮接法 |

| W25Q64 CS | PB12 | 保持原接法 |
| W25Q64 SCK | PB13 | 保持原接法 |
| W25Q64 DO / MISO | PB14 | 保持原接法 |
| W25Q64 DI / MOSI | PB15 | 保持原接法 |
| W25Q64 VCC / GND | 原先已验证的 3.3V / GND | 不因 TJA1050 使用 5V 而改变 Flash 供电 |

LED 继续使用现有驱动电路；裸 LED 必须保留限流电阻。蜂鸣器这里接的是三脚模块的信号输入，不是用 GPIO 给蜂鸣器负载直接供电。

### 4.4 总线

```text
A 收发器 CANH ================= CANH B 收发器
         CANL ================= CANL
         GND  ----------------- GND

A 端 CANH/CANL 之间 120Ω；B 端 CANH/CANL 之间 120Ω。
```

检查模块是否已经焊接或通过跳线接入 120Ω，不能重复增加。两端断电后测 CANH 与 CANL 间电阻，正常双终端约为 60Ω，实际读数受板上其他电路影响。短线联调也使用双绞线和尽量短的支线。

第三节点后期接在线形总线中间，不增加第三个终端电阻。终端始终保留在物理两端。

## 5. 软件分拆依据

保留一个仓库，S02.1 已在现有 `Project.uvprojx` 中增加 `A_Environment`、`B_Manager` 两个构建目标。它们目前只运行启动诊断任务，后续逐步接入各自业务。原 `FreeRTOS_Rebuild` 继续用于原单板功能回归，不复制整份项目成两套长期维护的驱动。

三个目标共享一致的文件清单，通过每个文件的 `Include in Target Build` 决定参与哪些目标；不是把三个 main 一起链接。输出分开存放，避免 A/B 固件相互覆盖。Keil 关于按目标包含/排除文件的说明见 [官方多目标文档](https://www.keil.com/support/docs/1902.htm)。

| 层 | A | B |
|---|---|---|
| 入口（已建立） | User/main_environment.c | User/main_manager.c |
| 最终业务任务（待接入） | Sensor、CAN 服务 | CAN 服务、StateMachine、Key、Display、Alarm、Record |
| 共用驱动 | CAN、TIM2、OLED、可选 UART | CAN、OLED、Key、LED、Buzzer、SPI2/W25Q64、UART |
| 配置所有者 | A 的采样与通信状态 | B 的阈值、界面与监测开关 |

CAN 接收 ISR 只取帧、入队并记录溢出；解析、OLED、日志、Flash 写入都在任务中完成。按现有 FreeRTOS 配置，ISR 调用 FromISR 接口时使用正确的优先级分组和允许的优先级范围，S02/S04 时落实。

B 的 CAN 服务是远程数据入口，替代原 Sensor 对显示/报警/历史队列的生产职责；每个消费者保留独立队列，不能让显示、报警和历史互相抢同一条消息。最新值可以覆盖，通信收包队列必须显式处理满队列。

B 的 StateMachine 统一修改阈值并调用 Flash 保存。报警读取两个阈值时取得一致快照；不能把 volatile 当成完整的并发保护。SPI/Flash 锁与 OLED 锁的持有范围分开，不能在 CAN ISR 中保存 Flash。

资源按 C8 的 64KB Flash、20KB SRAM 验证。新增任务和队列后检查堆剩余与栈高水位；不根据未确认的芯片扩容假设增加资源预算。

### 10.1 本步目标与边界

### 10.2 配置与理由

1. 根据当前 system_stm32f10x.c，HSE×9→72MHz，APB1 /2→36MHz；初始化用 RCC_GetClocksFreq 再检查 PCLK1=36MHz，不满足时返回时钟错误。该检查根据寄存器和晶振常量推算，不是仪器实测。
2. PA12 使用复用推挽，PA11 使用浮空输入，不启用内部上拉到 3.3V。使用复位后的默认 CAN 引脚，不重映射到 OLED 所在 PB8/PB9，不改 SWD 引脚。
3. CAN_Mode_Normal；Prescaler=6、BS1=9tq、BS2=2tq、SJW=1tq。位速率为 36MHz/[6×(1+9+2)]=500kbit/s，采样点 (1+9)/12≈83.3%；SJW 不额外加进位时长。
4. 禁用时间触发和自动唤醒；启用自动 bus-off 管理，但本步无 bus-off 实测。CAN_NART=ENABLE 表示关闭自动重发，避免后续联调无 ACK 时硬件持续重发，发送重试和超时将在后续收发步骤实现；本步不调用发送函数。
5. 调用 CAN_DeInit 后使用 CAN_StructInit 并显式填写参数。当前标准库 CAN_Init 进入/退出初始化状态的轮询都有 INAK_TIMEOUT 计数上限；失败返回 CAN_BUS_INIT_CONTROLLER_ERROR，不新增无限轮询。

正常模式的同步依赖 CAN_RX 上的总线状态；参考 [ST RM0008 bxCAN 章节](https://www.st.com/resource/en/reference_manual/cd00171190.pdf)。本步只有初始化返回值和 Alive 可见，不能据此作链路成功结论。

## 11. 执行卡：S02.3 A→B 单向固定帧（已通过）

### 11.1 目标与数据

保持 500 kbit/s 正常模式，A 每秒尝试发送 0x581 标准数据帧，数据为 01 02 03 04 05 06 07 NN；NN 为尝试序号。B 校验 ID/IDE/RTR/DLC/固定前缀后才增加 RX，显示最后序号并输出串口日志。本步不发送温湿度，不代表正式采样业务。

### 11.2 接口与执行方式

- CAN_Bus_Init 配置过滤器 0：32 位掩码模式，匹配标准数据帧 0x581，送 FIFO0。ID 高半字为 0x581<<5，掩码高半字 0xFFE0、低半字 0x0006（比较 IDE/RTR）。A 使用相同过滤器但本步不处理接收。
- CAN_Bus_SendFrame 仅由唯一发送任务调用：无空邮箱立即 BUSY；提交后查询硬件完成状态，成功 OK、失败 FAILED；持续 pending 达 20ms 则请求取消并返回 TIMEOUT，等待期间每 tick 让出 CPU。取消尚未完成时，后续无邮箱仍立即 BUSY，不无限等待。NART 仍 ENABLE，不自动重发。
- CAN_Bus_TryReceive 有帧才读取；标准库 CAN_Receive 已释放 FIFO 条目，不重复释放。
- A 每秒更新 TX 成功和错误次数，尝试序号每次递增并回绕。硬件 TX OK（正常模式含 ACK）不等于 B 软件已解析。
- B 用同一启动任务按 10ms 周期轮询，单轮最多 3 帧，独立每秒更新 Alive。UART/OLED 处理会占用时间；这是 1Hz 联调方式，后续用 ISR/队列替代，不能当作高负载接收方案。
- B 拒绝短帧、遥控帧、扩展帧、错误 ID 或前缀；RX 按校验通过的实际帧数累计，本步不做去重或丢帧率结论。未收帧前序号显示 ---。

过滤器位布局依据 [ST RM0008，Figure 230](https://www.st.com/resource/en/reference_manual/rm0008-stm32f101xx-stm32f102xx-stm32f103xx-advanced-arm-based-32-bit-mcus-stmicroelectronics.pdf)。硬件过滤实验仍待实物执行，不根据寄存器配置声称不匹配帧测试已通过。

### 11.3 操作与验收

1. 两端断电。把 DHT11 从 B 移到 A：DATA→A 的 PA0，VCC→A 的 3.3V，GND→A 的 GND；B 不再接 DHT11。
2. 其余接线保持 S02.3：两端 PA11/PA12 与 TJA1050、CANH/CANL/GND、两端 120Ω 终端。
3. 重新打开工程，编译 `A_Environment`，烧到 A；B 继续运行已烧好的 `B_Manager`，本步不必重烧。
4. 串口可选，接 A 的 PA9，9600/8N1。

预期现象：

- A 屏第 1 行 `A S03.1 DHT11`，第 2 行 `CAN: init OK`，第 3 行 `T:xx H:xx` 每 2 秒刷新，第 4 行 `Alive:` 每秒递增。
- A 串口依次出现 S03.1 boot、`CAN init OK 500k normal`，之后每秒 `[A] TX 581 ...` 和 `[A] alive`，每 2 秒一条 `[A] DHT11 ok T=.. H=..`。
- B 屏 RX 仍每秒递增，说明 0x581 链路未被采样改造破坏。

失败判断：

- 第 3 行长期 `--` 且串口每 2 秒一条 `[A] DHT11 fail`：先查 DHT11 供电、地线和 DATA 是否插错排。

- B 的 RX 停止：说明 A 任务被卡住，优先确认是否停在 `data_Check`（按当前代码不应发生）。
- 数值长期为 0 或明显异常：先记录串口原始行和模块供电，不直接改时序常量。

### 13.3 帧格式与实现要点

0x181（DLC 8）：D0 版本=1，D1 本次采样尝试序号，D2 温度，D3 湿度，D4 结果（0 有效 / 1 失败），D5~D7 保留为 0。

- 失败时 D2/D3 强制写 0，绝不把上一次读数或初始化值当成本次环境值。
- 尝试序号每次采样后递增，**失败也消耗序号**，B 才能靠序号判断是否漏帧。
- 打包逐字节赋值，不 `memcpy` 结构体，避免编译器对齐和字节序差异。

0x701（DLC 8）：D0 版本=1，D1 心跳序号，D2 采样状态（0 等待首次 / 1 最近成功 / 2 最近失败），D3 最近一次采样序号，D4~D7 上电运行毫秒（uint32 小端）。

- 心跳每秒发一次，与采样结果无关：传感器坏了仍要证明节点活着。
- 运行时间由 `xTaskGetTickCount() * portTICK_PERIOD_MS` 得到，当前 1 tick = 1 ms；按无符号回绕处理，约 49.7 天一圈。
- 心跳状态与 0x181 结果来自同一份 `sample_state`，不会出现“帧说失败、心跳说成功”的矛盾。

### 13.4 操作与验收

接线不变，只烧 A；B 保持现有 `B_Manager` 固件运行。

预期现象：

- A 屏第 1 行 `A S03.2 181/701`，第 2 行 `TX:00000 E:00000`，第 3 行温湿度每 2 秒刷新，第 4 行 Alive 每秒递增。
- A 串口每秒一条 `[A] 701 seq=.. state=.. OK`，每 2 秒一条 `[A] 181 seq=.. res=0 T=.. H=.. OK`；TX 约每秒增加 1.5 次。
- B 屏 RX 停在 S02.3 的最后值、S 不再变化，这是过滤器只认 0x581 的结果；B 仍会对总线上的合法帧回 ACK，所以 A 的发送结果是 OK 而不是 FAILED。

失败判断：

- A 的 E 持续增长、TX 不增长：总线没有 ACK（B 未上电、CANH/CANL 接反、终端电阻缺失）。
- 0x181 的 res 一直是 1：回到 S03.1 的 DHT11 排查路径，不要先怀疑 CAN。
- B 的 RX 恢复增长：说明 B 被烧回了旧固件或过滤器被改过，与本步预期不符。

### 14.3 设计要点

- 为什么必须用两个过滤器组：0x181 = 0b001_1000_0001，0x701 = 0b111_0000_0001，11 位 ID 里只有 bit0 相同。想用一个掩码同时放行两者，掩码会退化成只剩 bit0，等于放行所有奇数 ID。因此组 0 精确匹配 0x181、组 1 精确匹配 0x701，都投 FIFO0，应用层按 ID 分流。
- `CAN_FilterInit` 每次调用自行进入并退出过滤器初始化模式（FMR.FINIT），并置位 FA1R 中对应组；连续调用两次不会把第一组关掉。
- 失败样本不覆盖旧值：收到 res=1 时状态置 2，屏幕显示 `--` 与 `ERR`，但内部保留的旧数值不再显示。协议里 D2/D3 的 0 只是占位，不能当真实读数。
- 屏幕分工：第 1 行身份 + 心跳计数，第 2 行温湿度 + 结果，第 3 行合法采样计数 + 最后序号，第 4 行 Alive。心跳计数放第 1 行是因为它是“A 是否还活着”的直接证据，比放在第三行更容易一眼看到。
- 结果位固定占 3 个字符（`OK ` / `ERR` / `---`），否则上一次的 `ERR` 会被 `OK` 覆盖成 `OKR`。
- 串口仍在接收循环里同步输出，9600 下一行约 20~30 ms，会拉长单轮周期。当前 1.5 帧/秒无影响，S06 改中断 + 队列时一并处理。

### 14.4 操作与验收

接线不变，只烧 B；A 保持 S03.2 固件运行。

- B 屏第 1 行 `B S04.1 HB:00012`，每秒 +1。
- 第 2 行 `T:25 H:60 OK`，每 2 秒刷新，数值与 A 屏一致。
- 第 3 行 `RX:00003 S:002`，RX 每 2 秒 +1，S 等于 A 的最近采样序号。
- 第 4 行 `Alive:` 每秒 +1。
- 串口：每秒 `[B] alive` 和 `[B] 701 ...`，每 2 秒 `[B] 181 ...`。

故障验收：拔掉 A 的 DHT11，B 第 2 行变 `T:-- H:-- ERR`，但第 1 行 HB 仍每秒 +1、第 3 行 RX 仍每 2 秒 +1。这条用来证明“传感器故障”和“节点离线 / 通信中断”在 B 上是两个独立信号。

失败判断：

- B 的 RX 不涨：先看 A 的 TX 是否在涨；若 A 正常而 B 不动，看 `g_manager_rejected_frames`，区分“没收到”和“收到但不合格”。
- RX 在涨但第 2 行一直是 `--`：多为版本字段不符或 D4 越界，对照串口原始行的 res 值。
- HB 不涨而 RX 在涨：只激活了组 0，检查组 1 是否配置成功。

## 15. 执行卡：S04.2 B 端有效性判定

### 15.1 目的与边界

### 15.3 设计要点

- 两个超时故意不同。心跳 1 秒一次，`3000 ms` 没来判离线；采样 2 秒一次，`5000 ms` 没有新样本才判过期。若采样也用 3 秒，丢一帧（间隔 4 秒）就会误报过期，屏幕上会周期性闪 OLD。
- 重复帧（序号等于上一条）直接丢，而且**不刷新时间戳**。如果刷新，重复帧会让数据年龄永远年轻，过期判定彻底失效。这是“收到了”和“是新数据”必须分开的典型例子。
- 漏帧算法：`gap = (seq - last - 1)`。1~10 计入漏帧数；大于 10 只打日志，因为那更像 A 重启或长时间中断，计进去会把统计冲成大数。序号是 8 位，减法在 uint8 下自然回绕，255→0 不会被误判为跳变。
- 重启识别用 0x701 的运行时间回退。识别到后清空序号基线，否则 A 重启后的第一个低序号会被当成重复帧丢掉。已知局限：uptime 是 32 位毫秒，约 49.7 天回绕时也会触发一次误判，V1 接受。
- 量程只拦明显不可能的值：有效样本 0~60℃ / 0~100%RH。DHT11 标称 0~50℃ / 20~90%RH，放宽是为了不替传感器做精度判断。无效样本（res=1）要求 D2/D3 必须为 0，这是协议约定，违反就计入 rejected。
- 在线显示三态：未知 / 在线 / 离线。上电后没收到心跳显示 `A:--`，不冒充“在线”——这和“没有数据就显示 --”是同一条原则。
- 数据四态：`---` 从未收到、`OK` 新鲜有效、`ERR` 本次读取失败、`OLD` 过期或离线。确认离线时**立即**降级为 OLD，不等 5 秒过期阈值：链路都断了，数据不可能还可信。
- 只在状态变化时刷屏和打日志。10 ms 循环里无条件刷屏会拖垮串口（9600 下一行 20~30 ms）。

### 15.4 操作与验收

接线不变，只烧 B；A 保持 S03.2 固件。

上电预期：第 1 行先 `A:--`，1 秒内变 `A:ON `；2 秒后第 2 行出现 `T:xx H:xx OK`。

三个必做实验：

1. **拔 A 的 DHT11**：第 2 行变 `T:-- H:-- ERR`，第 1 行保持 `A:ON`，第 3 行 RX 继续每 2 秒 +1。证明“传感器坏”不等于“节点掉线”。
2. **断 A 的电（或拔掉 CANH/CANL）**：3 秒内第 1 行变 `A:OFF`，同一时刻第 2 行变 `OLD`。恢复后回到 `A:ON` 与 `OK`。
3. **让 A 重新上电**：串口出现 `[B] A restarted up=...`，第 3 行的 S 从 0 重新开始，且不会被误判成重复帧。

失败判断：

- 断电后一直 `A:ON`：心跳超时没生效，先确认 `TickType_t` 的差值比较没有被写成有符号数。
- `A:OFF` 但 A 明明在发：看 `g_manager_rejected_frames` 是否在涨，可能是心跳帧被判不合格。
- ERR 与 OK 频繁交替：是 A 端 DHT11 供电或时序不稳，不是 CAN 问题，回到 S03.1 的排查路径。
- 第 3 行 S 长时间不动但 RX 在涨：只有重复帧会这样，说明 A 的序号没有递增。

### 16.3 设计要点

- 为什么要队列：接收任务的唯一职责是尽快把 FIFO 取空。写历史、刷 OLED 都可能变慢（S05 的整屏重绘走软件 I2C，一次几十毫秒），若在同一任务里串行执行，FIFO 只有 3 格，很快就会溢出丢帧。队列把“收”和“处理”分开，这就是“页面切走仍收包”的技术前提。
- 句柄为什么定义在 `main_manager.c`：单板版的 `recordQueue` / `historyMutex` 定义在 `User/main.c`，B 目标不编译 `main.c`。所有 FreeRTOS 资源统一由目标入口创建，任务文件保持“只使用、不创建”。
- 只让 `res=0` 入队：失败帧的 D2/D3 是占位 0，写进历史就是两条假的 0℃/0%RH。历史里出现假数据比缺一条更糟。
- 入队超时写 0：宁可少存一条，也不让接收任务在队列上等。失败条数记在 `g_manager_history_dropped`，不静默丢。
- 队列深度 4：采样 2 秒一条，写入是纯内存操作，4 条足够吸收抖动；再深只是白占 RAM。
- 每 10 秒转储一次：不打日志就无法证明“写进去的内容和顺序是对的”。转储期间持有 `historyMutex`，因为 `history_temp` 和 `history_humi` 是分开写的，裸读可能拿到“温度是新的、湿度是旧的”这种撕裂组合。
- 已知取舍：`H:n` 只显示条数（0~4），具体内容看串口；历史页面留到 S05。

### 16.4 操作与验收

预期现象：

### 19.3 设计要点

- 为什么必须在调度器启动前读：Flash 驱动用 TIM2 做短时等待，此时 `vTaskDelay` 还不能用。这与单板版 `User/main.c` 的初始化顺序一致，不是新发明的时序。
- 为什么不用判断返回值再决定赋值：`ThresholdStore_Init()` 先把默认值写进输出参数，再尝试扫描 Flash。即使芯片没接、返回 `flash_error`，输出参数里已经是默认值。所以无条件赋值是安全的，返回值只用于日志——这样不会出现“读取失败导致阈值变成未初始化值”的情况。
- 为什么把 `driver=` 也打出来：`load=defaults` 可能是空片，也可能是芯片没响应，两者处理方式完全不同。`driver=0` 表示 Flash 通信正常，非 0 就是 SPI/接线问题，一眼可分。

### 20.1 目的与边界

### 20.3 设计要点

- 队列长度必须为 1：报警只关心“最新一次判断”，用 `xQueueOverwrite` 覆盖写，消费慢也不会堆积过期值。
- 失败样本送 0：这一轮传感器没读到，就不能拿上一次的高温继续鸣叫。屏幕显示 `NO DATA: SENSOR`，声光同时停。
- 数据过期/离线也送 0：值已经不可信，继续按它闪烁等于用旧数据报警。
- 为什么不在报警任务里判断“数据新不新”：`task_alarm.c` 是和单板版共用的文件，它只知道阈值和 `currentState`。把“有效性判断”放在数据源头（接收任务）做，共享文件一行不用改——这是本步最重要的取舍。
- 报警跟随 `currentState`：STOP 和菜单页不响，与单板版语义一致（STOP = 暂停监控）。
- 已知取舍：数据失效时是“静音 + 屏幕提示”，而不是“另一种声光节奏”。工业上更常见的是独立故障报警（例如慢闪），那需要改共享任务或另写一个报警任务，留作扩展。

4. 拔掉 A 的 DHT11：屏幕 `NO DATA: SENSOR`，**声音必须停**——不能按上一次的值继续响。

- 超阈值不响：`alarmQueue` 没被写入，检查 `xQueueOverwrite` 是否在采样分支里执行。

### 21.3 设计要点

- TEC/REC 用标准库 `CAN_GetLSBTransmitErrorCounter` / `CAN_GetReceiveErrorCounter`：位段位置很容易记错（REC 在寄存器 31:24，不是 15:8），让库去处理即可。
- **LEC 不能走库函数**：本仓库这版 SPL 的 `CAN_GetLastErrorCode()` 少了 `>> 4`，LEC=3 会被读成 0x30，串口上显示成 `lec=48`（2026-11-15 实物发现）。改为按 RM0008 的 bit6:4 自己取，函数见 `CAN_Bus_ReadErrorStatus()`。
- BOFF/EPV 只能自己读：标准库头文件没有导出这两个掩码，按 RM0008 的 bit2 / bit1 用命名常量取，不写魔数。
- 打印节流：9600 波特下一行约 50 字符 ≈ 52 ms，每秒刷会挤掉应用日志。原设计“只在变化时打印”有个缺陷——TEC 一旦冻结，日志整段消失，分不清“没变化”和“任务死了”。现改为变化时立刻打、不变时每 5 秒补打一行。
- 为什么不能只看“发送成功/失败”：失败是现象，TEC 是程度。TEC 到 128 进入**错误被动**（还能发，但出错后要让位），到 255 进入**bus-off**（彻底退出总线）。三个阶段在日志里是能看见的。
- B 的统计行 10 秒一次：S07 要跑 30 分钟，屏幕数字记不住，必须有可复制的文本。

### 21.4 操作与验收

接线不变，**A、B 都重烧**。

实验一（正常）：
- A 上电后出现一行 `[A] can tec=0 rec=0 lec=0(none) boff=0 epv=0`，之后不再出现。

实验二（断总线，拔 CANH 或 CANL 任意一根）：
- 先读 21.6：只有“对端不在、没人回 ACK”这一类错误在 TEC≥128 后会停止累加，永远到不了 bus-off；本实验靠**位错误/格式错误**才有机会突破 128，能否突破必须实测，不能照抄下表。
- A 的错误计数开始增长，每秒一行 can 日志，TEC 通常按 8 递增：8 → 16 → … → 128（此时 `epv=1`）→ … → 255（`boff=1`）。
- 进入 bus-off 后有两种可能，**都要如实记录**：
  1. 总线悬空被读成连续隐性位 → `ABOM` 在几毫秒内自动恢复，日志出现 `tec=0 … boff=0`，然后再次爬升，形成锯齿；
  2. 环境噪声让隐性位不连续 → 停在 `boff=1` 不恢复。
- 恢复接线后，无论哪种情况都应回到 `tec=0 boff=0`，A 的 TX 重新增长。

实验三（A 断电）：
- B 端 3 秒内转 `NO DATA: STALE`，10 秒统计行里 `hb` 停止增长。
- A 重新上电后，B 打印 `[B] A restarted`，`rst` +1。

实验四（恢复需要新数据）：
- A 恢复后，B 在**第一帧新数据到达前**保持 `NO DATA`，不会拿旧值冒充。

注意事项：

- 拔线实验会让 A 进入 bus-off，这是预期行为，不是故障扩散。
- **不要**用“B 的接收停了”推断 bus-off：那只说明 B 收不到帧。bus-off 是 A 的控制器状态，只能看 A 的日志。
- 这条正好回应第 7 节那句“对端掉线不等于必然进入 bus-off”——只有一个节点时没有 ACK，TEC 才会累积；有第三个节点在总线上回 ACK 时，情况完全不同。

### 21.6 实测记录：TEC 为什么停在 128（2026-11-15）

**现象**（拔掉 B 的电源，A 端串口持续输出）：

```
[A] can tec=128 rec=0 lec=3(ack) boff=0 epv=1 seen=0 tx=175/114
[A] can tec=128 rec=0 lec=3(ack) boff=0 epv=1 seen=0 tx=175/122
```

- `tec` 从 0 按 8 递增到 128 后**不再变化**；
- `lec` 固定为 3（ACK 错误），`rec` 恒为 0；
- `epv=1`（已进入错误被动），`boff=0`、`seen=0`（从未进入 bus-off）；
- `tx` 的成功数冻结在 175，失败数每帧 +1。

**结论：这是 ISO 11898-1 的规定行为，不是代码 bug。**

ISO 11898-1 错误计数规则的例外 1：**节点处于错误被动状态时，若因收不到显性 ACK 而报 ACK 错误，且在发送被动错误标志期间也没有检测到显性位，则 TEC 不增加。**

推导：TEC 每次发送失败 +8，16 次失败到 128 进入错误被动；此后失败仍被识别为 ACK 错误（`lec` 一直保持 3），但计分停止。所以 TEC 的天花板是 128，**永远到不了 256，也就永远不会 bus-off**。

设计意图：整条总线断电或只剩一个节点时，它不该把自己永久隔离。故障收敛机制针对的是“自己坏”，不是“对端不在”。

**排除的其它假设**（用已有日志即可排除，不必再测）：

| 假设 | 为什么排除 |
|---|---|
| 邮箱拥堵 | 无空闲邮箱时 `CAN_Transmit` 返回 `CAN_TxStatus_NoMailBox`，代码返回 `CAN_BUS_TX_BUSY`，日志应出现 `BUSY`；实测全是 `FAILED` |
| 超时被取消 | 超时分支返回 `CAN_BUS_TX_TIMEOUT`，日志应出现 `TIMEOUT`；实测没有 |
| 控制器卡在初始化模式 | B 重新上电后 TEC 从 128 逐帧 −1 降到 0，收发全程正常，说明模式没问题 |
| 帧没发上总线 | 没发出去的帧会保持 Pending，20 ms 后走超时取消返回 `TIMEOUT`；而 `CAN_TxStatus_Failed` 要求 RQCP=1 且 TXOK=0，即“请求已完成但未成功”，前提是真的发过 |
| 读错寄存器 | `lec=48` 确实是读错（`CAN_GetLastErrorCode` 漏了 `>>4`），已修；修好后 `lec=3` 与现场一致 |

**对 S06.2 的影响**：拔对端电源只能验证到 `tec=128 / epv=1`，**不能**用来验证 bus-off。要让 TEC 突破 128，必须有非 ACK 类错误（位错误、填充错误、格式错误、CRC 错误），这些在错误被动状态下仍然 +8。候选做法：拔单根 CANH 或 CANL、CANH 与 CANL 短接、强干扰。**三种均未实测，结论待定。**

### 21.7 bus-off 复现尝试记录（2026-11-15）

| # | 操作 | 观察 | 结论 |
|---|---|---|---|
| 1 | 拔掉 B 的电源 | `tec` 顶在 128 不动，`lec=3(ack)`，`seen=0` | 纯 ACK 错误，被错误计数例外豁免，**到不了 bus-off** |
| 2 | 拔掉单根 CANH | `lec` 仍为 3，`tec` 仍在 128 附近 | 断点在收发器之外，A 的本地回读完好，只表现为“对端收不到” |

| 4 | CANH 接地 | 未复现 | 初步判定：短路未真正落在 A 的收发器引脚上，或未共地 |
| 5 | **A 端波特率错配**（`CAN_Prescaler` 12 = 250k，B 保持 6 = 500k） | TEC 128 → 248 后**骤降为 0**，`esr` 从 `0AF80033` 变 `00000050` | ✅ **复现成功**，见 21.8 |

**仍未做的可选路径**（都需要独立小步骤，不阻塞 S06 其余验收）：

1. `CAN_IT_ERRI` 错误中断，在 ISR 里锁存 `BOFF` 位并计数——把 2.8 ms 的瞬态变成可读数字；
2. B 端波特率错配（`Hardware/CAN_Bus.c` 第 83 行 `CAN_Prescaler` 6 → 12），让 B 持续发错误帧打断 A，制造稳定位错误。

**验收口径**：bus-off 未复现就记“未复现”，不得用“应该会 bus-off”的推断替代实测。

### 21.8 bus-off 复现成功（2026-11-15 19:20）

**做法**：A 端 `Hardware/CAN_Bus.c` 第 83 行 `CAN_Prescaler` 由 6 改 12（500k → 250k），B 端保持 6（500k），只烧 A。

**机制**：A 用 250k 发帧，B 用 500k 采样 → B 解出乱码、检测到填充/格式错误 → B 在总线上发错误帧（6 个连续显性位）→ 这些显性位插进 A 正在发的帧里 → A 报位错误（`lec=4 bit-rec` 或 `lec=5 bit-dom`）→ **位错误不属于豁免项**，TEC 照常 +8。

**关键日志（末两行）**：

```
[A] can tec=248 rec=10 lec=3(ack)   boff=0 epv=1 seen=0 tx=0/168 esr=0AF80033 msr=00000C00
[A] can tec=0   rec=0  lec=5(bit-dom) boff=0 epv=0 seen=0 tx=0/169 esr=00000050 msr=00000C00
```

`esr` 解码：

| | 前一行 | 后一行 |
|---|---|---|
| REC | 10 | **0** |
| TEC | 248 | **0** |
| LEC | 3 | 5 |
| BOFF | 0 | 0 |
| EPV | 1 | **0** |
| EWGF | 1 | 0 |

**三条独立证据证明发生了 bus-off**：

1. `TEC 248 → 0`：`tx` 成功数为 0（`tx=0/169`），没有任何“发送成功 −1”的可能，唯一能把 TEC 归零的机制就是 bus-off；
2. `REC 10 → 0`：bus-off 会同时清零两个计数器；
3. `EPV 1 → 0`：节点从错误被动回到错误主动，说明重新完成了一次状态复位。

之后 TEC 又从 0 开始重新累加，形成用户观察到的**锯齿**——这正是 ABOM 自动恢复的标志（不按复位也能自己回来）。

**为什么 `boff` 和 `seen` 仍是 0**：bus-off 状态只持续到总线连续 128×11 个隐性位（500k 下约 2.8 ms）就被 ABOM 清掉，而快照每秒才取一次，命中概率约 0.3%。**要把“进过几次 bus-off”做成确定数字，必须加 `CAN_IT_ERRI` 中断在 ISR 里锁存 BOFF 位**，这是 S06.2 剩余工作。

**实验边界**：本次是“人为制造波特率错配”触发的 bus-off，用于验证故障收敛行为；正常固件两个目标都是 `CAN_Prescaler = 6`（500k），实验后已改回。A 端当前代码为 6，第 83 行下方保留一行注释掉的 `// can.CAN_Prescaler = 12;` 作为实验痕迹，是否清理待定。
