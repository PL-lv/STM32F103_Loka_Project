# CAN 升级协作约定

本目录的 CAN 升级按 `docs/CAN开发流程.md` 执行。开始相关工作前先读该文档的当前阶段、接线和验收记录。

- 用户已自行完成 CAN 基础理论和单设备回环；不要重新从空工程或回环教程开始。
- 当前目标是 A 环境端采样上报、B 管理端显示/按键/报警/阈值保存。旧方案中把报警留在 A、通过 CAN 给 A 设置阈值的安排已被替代。
- A 另有 OLED 用于本地诊断；S02.1 与 B 一样在屏幕显示身份和运行计数，管理菜单仍由 B 负责。
- 每次只推进当前阶段中的一个小步骤。先说明目的、具体文件和原因，再做小范围修改，说明验证方法和预期结果。
- 用户已明确：代码和固件工程配置由助手按当前小步骤实现；每步结束必须讲清目的、具体文件/函数、关键改动和验证结果。用户负责硬件接线、烧录和实物反馈，并可随时提问。不要再要求用户亲自写代码，也不要一次性写完整个升级。
- 编译通过与实物通过分别记录；需要用户操作的接线、烧录和实物验收未确认前，不跨过该验收门槛继续下一阶段。
- 不一次性生成全部 A/B 固件，不因工期压力跳过讲解或实物验收。
- Keil 负责固件构建和烧录；CMake 当前只负责 CLion 索引。
- 保留用户现有改动和同仓库其他子项目。构建验证使用隔离输出，避免覆盖仓库内已跟踪的 Objects/Listings 产物。
- 新增或修改带中文注释的 C/H 保持 UTF-8 BOM，避免已有 Keil 环境误读编码。
- 需求变化时先在开发流程文档中说明影响，更新节点职责、协议或接线，再修改对应代码。
